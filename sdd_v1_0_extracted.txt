TỔNG QUAN HỆ THỐNG 1.1 Mục đích và phạm vi Hệ thống Quản lý, ứng dụng và phát triển CNTT là hệ thống thu thập, tổng hợp và báo cáo số liệu thực lực công nghệ thông tin (CNTT) trong lực lượng Công an nhân dân (CAND). Hệ thống cho phép các đơn vị địa phương nhập liệu định kỳ trên 12 mô-đun nghiệp vụ, tổng hợp thành báo cáo dạng snapshot, thực hiện quy trình phê duyệt và xuất kết quả ra định dạng PDF. Tài liệu này mô tả thiết kế kỹ thuật tổng thể của hệ thống, bao gồm kiến trúc phần mềm, mô hình dữ liệu, các phân hệ nghiệp vụ, quy trình báo cáo, thiết kế API và chính sách bảo mật. Phạm vi hệ thống • Quản lý kỳ báo cáo: Theo chu kỳ tháng, quý, năm. • Nhập liệu: 12 mô-đun nghiệp vụ theo đơn vị. • Báo cáo snapshot: Tạo, nộp, khóa và xuất PDF. • Yêu cầu bổ sung: Mở lại snapshot đã khóa để chỉnh sửa và nộp lại. • Quản lý người dùng: Phân quyền dựa trên permission. 1.2 Các bên liên quan và vai trò Vai trò Mô tả Quyền điển hình System Admin Quản trị toàn hệ thống, cấu hình, phân quyền Tất cả quyền (system:admin) Admin cấp Bộ Quản lý kỳ báo cáo, phê duyệt yêu cầu bổ sung ky_bao_cao:approve, yeu_cau_bo_sung:approve Cán bộ nhập liệu Nhập dữ liệu các mô-đun nghiệp vụ của đơn vị { mô-đun }:read/create/update/delete Cán bộ nộp báo cáo Tạo bản thảo snapshot, nộp báo cáo định kỳ snapshot:create/submit 1.3 Công nghệ và nền tảng Thành phần Công nghệ / Phần mềm Backend API .NET 8, ngôn ngữ C# Frontend Angular (Single Page Application) Cơ sở dữ liệu Oracle Database Quản lý migration DB Flyway Lưu trữ tệp MinIO (giao thức tương thích S3) Xuất PDF Gotenberg (chuyển đổi sang PDF) Ghi nhật ký Serilog (structured logging) Xác thực JWT Bearer Token, ASP.NET Identity ORM Entity Framework Core 1.4 Môi trường triển khai Hệ thống được triển khai theo mô hình tập trung, trong đó toàn bộ các thành phần chạy trong mạng nội bộ CAND. Không có kết nối internet trực tiếp; trình duyệt của người dùng kết nối qua mạng nội bộ đến API Server. Sơ đồ triển khai tổng thể được mô tả dưới đây. KIẾN TRÚC PHẦN MỀM 2.1 Phân lớp Clean Architecture Dự án tuân theo nguyên tắc Clean Architecture. Dependency rule được áp dụng nghiêm ngặt: các lớp bên trong không phụ thuộc vào lớp bên ngoài. Bốn lớp từ ngoài vào trong được phân chia như sau: Hình 2: Phân lớp Clean Architecture — Dependency rule 2.2 Vertical Slice trong Application layer Mỗi mô-đun nghiệp vụ được tổ chức thành một thư mục độc lập (Vertical Slice) trong lớp Application. Mỗi slice chứa: file DTO (Data Transfer Object) và file Service. Controller trong lớp Api gọ trực tiếp Service qua interface đã đăng ký trong Dependency Injection container. (mỗi mô-đun một thư mục độc lập) 2.3 Middleware Pipeline Mỗi HTTP request đến hệ thống đi qua chuỗi middleware theo thứ tự sau trước khi đến Controller Action: HTTP Request đến ↓ CorrelationIdMiddleware — Gán X-Correlation-Id vào mỗi request ↓ SecurityHeadersMiddleware — Bổ sung các security header (CSP, HSTS...) ↓ RequestLoggingMiddleware — Ghi nhật ký request và response ↓ GlobalExceptionMiddleware — Bắt ngoại lệ, trả về ApiResponse lỗi chuẩn hóa ↓ RateLimiter — Giới hạn tần suất gọi API ↓ JWT Authentication — Xác thực Bearer Token ↓ Permission Authorization — Kiểm tra quyền [HasPermission(...)] ↓ Controller Action — Xử lý logic nghiệp vụ Hình 3: Middleware Pipeline — Thứ tự xử lý request trong .NET CHƯƠNG 3. MÔ HÌNH DỮ LIỆU 3.1 Quy ước đặt tên bảng Toàn bộ các bảng trong cơ sở dữ liệu tuân theo quy ước đặt tiền tố (prefix) để phân loại chức năng: Prefix Ý nghĩa Ví dụ SYS_ Bảng hệ thống: người dùng, vai trò, mã danh mục SYS_USERS, SYS_CODES, SYS_CODE_VALUES BIZ_ Bảng nghiệp vụ: dữ liệu nhập liệu của đơn vị BIZ_NHAN_LUC_CNTT, BIZ_DU_AN_CNTT RPT_ Bảng báo cáo: kỳ, snapshot, file, trạng thái RPT_KY_BAO_CAO, RPT_BAO_CAO_SNAPSHOT REF_ Bảng danh mục tham chiếu dùng chung REF_DON_VI, REF_LOAI_THIET_BI 3.2 Phân loại Group A và Group B Các bảng BIZ_ được phân thành hai nhóm dựa trên tính chất dữ liệu: Nhóm Đặc điểm Ý nghĩa Ví dụ Group A Không có cột KY_BAO_CAO_CODE Phản ánh trạng thái hiện tại — không gắn với kỳ cụ thể BIZ_NHAN_LUC_CNTT, BIZ_HE_THONG_THONG_TIN Group B Có cột KY_BAO_CAO_CODE Dữ liệu sự kiện theo từng kỳ báo cáo BIZ_DAO_TAO_BOI_DUONG, BIZ_VAN_BAN_QPPL Cột KY_BAO_CAO_CODE là chuỗi định danh kỳ báo cáo, ví dụ: "2026Q1" (quý 1 năm 2026), "2026M01" (tháng 01/2026), "2026" (cả năm). 3.3 Pattern SYS_CODES / SYS_CODE_VALUES Toàn bộ giá trị danh mục (dropdown, enum, lookup) được lưu tập trung trong hai bảng SYS_CODES và SYS_CODE_VALUES thay vì tạo bảng riêng cho từng loại. Cấu trúc: SYS_CODES: CODE NVARCHAR2(100) PK -- Khóa định danh nhóm danh mục NAME NVARCHAR2(500) -- Tên hiển thị nhóm IS_ACTIVE NUMBER(1) -- Đang sử dụng IS_SYSTEM NUMBER(1) -- Không được xóa SYS_CODE_VALUES: CODE NVARCHAR2(100) FK → SYS_CODES.CODE VALUE NVARCHAR2(100) -- Giá trị lưu vào cột nghiệp vụ NAME NVARCHAR2(500) -- Tên hiển thị SORT_ORDER NUMBER(4) -- Thứ tự hiển thị Các bảng nghiệp vụ tham chiếu bằng cách lưu VALUE (chuỗi) vào cột tương ứng. Ví dụ: cột TINH_TRANG_PHE_DUYET lưu giá trị "DA_PHE_DUYET". Không dùng khóa ngoại — giữ tính linh hoạt khi thêm/sửa danh mục. 3.4 REF_DON_VI — Cây tổ chức đơn vị Bảng REF_DON_VI được tổ chức dạng cây tự tham chiếu thông qua cột PARENT_ID. Mỗi bản ghi đại diện cho một đơn vị trong cơ cấu tổ chức CAND. Các cột bổ sung tại migration V29: Cột Kiểu dữ liệu Ý nghĩa CAP_DON_VI NVARCHAR2(50) Cấp đơn vị — CodeValue: BO / CUC / TINH / PHONG / XA / HOC_VIEN WEBSITE_NOI_BO NVARCHAR2(500) URL cổng thông tin nội bộ của đơn vị WEBSITE_INTERNET NVARCHAR2(500) URL cổng thông tin internet công khai TONG_BIEN_CHE NUMBER(10) Tổng biên chế của đơn vị Các chỉ tiêu "Số đơn vị cấp Phòng trực thuộc" và "Số đơn vị cấp Xã trực thuộc" được tính động từ cây đơn vị (dùng đếm bản ghi con theo CAP_DON_VI) — không lưu vào cơ sở dữ liệu. 3.5 Tổng quan mô hình dữ liệu Sơ đồ ERD-C-01 dưới đây thể hiện tổng quan 5 nhóm bảng và quan hệ chính giữa các nhóm. Đây là nguyên tắc nhất quán đảm bảo người dùng không thể đọc hoặc ghi dữ liệu của đơn vị khác nếu không có quyền đặc biệt. private bool HasCrossDonViPermission() => _user.HasPermission(Permissions.SystemAdmin) || _user.HasPermission(Permissions.KyBaoCao.Approve); private IQueryable<Entity> ApplyReadScope(IQueryable<Entity> q) { if (!HasCrossDonViPermission()) q = q.Where(x => x.DonViId == _user.DonViId); return q; } private async Task EnsureValidScopeAsync(long donViId) { if (!HasCrossDonViPermission() && donViId != _user.DonViId) throw new ForbiddenException(" MÔ-ĐUN _SCOPE_DENIED"); } 7.3 Soft Delete Tất cả entity BIZ_ và RPT_ kế thừa class cơ sở AuditableSoftDeleteEntityBase có cột DELETED_AT. YÊU CẦU PHI CHỨC NĂNG 9.1 Hiệu năng (Performance) Hệ thống Quản lý, ứng dụng và phát triển CNTT phải đáp ứng các chỉ tiêu hiệu năng sau đây để đảm bảo trải nghiệm người dùng và khả năng xử lý trong giờ cao điểm thu thập số liệu: Chỉ tiêu Giá trị mục tiêu Thời gian phản hồi API (P95) ≤ 500ms cho các endpoint CRUD đơn giản; ≤ 2s cho BuildSnapshotJson Thời gian sinh PDF (P95) ≤ 30 giây cho một snapshot đầy đủ 12 mô-đun Số người dùng đồng thời ≥ 200 phiên đồng thời (concurrent sessions) trong giờ cao điểm Throughput API ≥ 100 request/giây trên toàn hệ thống Thời gian tải trang đầu tiên (FCP) ≤ 3 giây trên mạng nội bộ CAND Kích thước Snapshot JSON ≤ 512 KB (hard limit — reject nếu vượt) Kích thước file PDF ≤ 10 MB (hard limit) Lưu ý: Các chỉ tiêu trên được đo trên môi trường triển khai thực tế (mạng nội bộ CAND), không áp dụng cho môi trường phát triển local. 9.2 Khả năng mở rộng (Scalability) Hệ thống được thiết kế để mở rộng theo chiều dọc (vertical scaling) trong giai đoạn hiện tại, với khả năng chuyển sang mở rộng chiều ngang khi cần: • Cơ sở dữ liệu Oracle hỗ trợ connection pooling và partitioning khi lượng dữ liệu tăng. • API Server (.NET 8) hỗ trợ chạy nhiều instance phía sau Load Balancer do thiết kế stateless (JWT authentication). • MinIO hỗ trợ distributed mode khi cần mở rộng dung lượng lưu trữ. • Dữ liệu ước tính: khoảng 6.000+ đơn vị (từ cấp Bộ đến cấp Xã), mỗi đơn vị tối đa 12 mô-đun , 12 kỳ báo cáo/năm. 9.3 Tính sẵn sàng (Availability) Chỉ tiêu Giá trị mục tiêu Uptime mục tiêu ≥ 99.5% (tương đương ≤ 44 giờ downtime/năm) Thời gian bảo trì định kỳ Cửa sổ bảo trì: 22:00 – 06:00 Chủ nhật hàng tuần Recovery Time Objective (RTO) ≤ 4 giờ Recovery Point Objective (RPO) ≤ 1 giờ (backup incremental mỗi giờ) 9.4 Tính tương thích (Compatibility) Frontend Angular hỗ trợ các trình duyệt sau trên mạng nội bộ CAND: Trình duyệt Phiên bản tối thiểu Google Chrome Phiên bản 90+ Microsoft Edge (Chromium) Phiên bản 90+ Mozilla Firefox Phiên bản 88+ Safari Không hỗ trợ (không sử dụng trong mạng CAND) Hệ thống yêu cầu độ phân giải màn hình tối thiểu 1366×768 pixel. Responsive design hỗ trợ đến độ phân giải 1920×1080 (Full HD). 9.5 Bảo mật phi chức năng • Mật khẩu lưu dạng hash (BCrypt, work factor ≥ 12). • JWT Token có thời hạn tối đa 8 giờ (một ca làm việc). • Rate Limiting: tối đa 60 request/phút/user cho các endpoint nhạy cảm (login, submit). • Security Headers: CSP, HSTS, X-Content-Type-Options, X-Frame-Options được cấu hình qua SecurityHeadersMiddleware. • Toàn bộ giao tiếp trong mạng nội bộ sử dụng HTTPS/TLS 1.2+. XỬ LÝ LỖI VÀ KHÔI PHỤC 11.1 Chiến lược xử lý lỗi (Error Handling Strategy) Hệ thống triển khai chiến lược xử lý lỗi tập trung thông qua GlobalExceptionMiddleware. Mọi ngoại lệ phát sinh trong pipeline đều được bắt và chuyển đổi thành response chuẩn hóa: Loại ngoại lệ HTTP Status Error Code mẫu NotFoundException 404 Not Found VANBAN_NOT_FOUND, SNAPSHOT_NOT_FOUND ForbiddenException 403 Forbidden MÔ-ĐUN_SCOPE_DENIED, KY_NOT_OPEN BadRequestException 400 Bad Request INVALID_STATUS_TRANSITION, DUPLICATE_ENTRY ConflictException 409 Conflict SNAPSHOT_ALREADY_LOCKED, KY_ALREADY_KHOA UnauthorizedException 401 Unauthorized TOKEN_EXPIRED, INVALID_CREDENTIALS Unhandled Exception 500 Internal Server Error INTERNAL_ERROR (chi tiết ghi vào log, không trả client) 11.2 Logging và Monitoring Hệ thống sử dụng Serilog với structured logging. Mỗi request được gắn CorrelationId duy nhất (thông qua CorrelationIdMiddleware) để truy vết xuyên suốt từ request đến database query: • Log Level INFO: Ghi nhận mọi HTTP request/response (URL, status code, duration) qua RequestLoggingMiddleware. • Log Level WARNING: Business rule violation (ví dụ: nộp snapshot khi kỳ đã đóng), rate limit exceeded. • Log Level ERROR: Unhandled exception, lỗi kết nối database, lỗi gọi service ngoài (MinIO, Gotenberg). • Log destination: File log xoay vòng theo ngày (rolling daily), kết hợp output console cho môi trường phát triển. 11.3 Retry và Circuit Breaker Đối với các service ngoài (MinIO, Gotenberg), hệ thống áp dụng chiến lược retry với exponential backoff: Service Chính sách Retry MinIO (upload/download file) Retry 3 lần, backoff 1s → 2s → 4s. Nếu thất bại, trả lỗi 503 cho client. Gotenberg (sinh PDF) Retry 2 lần, backoff 2s → 5s. Timeout mỗi lần 60 giây. Nếu thất bại, snapshot giữ trạng thái Draft, thông báo lỗi cho người dùng. Oracle Database Connection pool tự retry kết nối. Nếu database không khả dụng > 30 giây, health check endpoint trả về Unhealthy. 11.4 Sao lưu và khôi phục dữ liệu (Backup & Recovery) Chiến lược sao lưu được thiết kế để đảm bảo RPO ≤ 1 giờ và RTO ≤ 4 giờ: Thành phần Chính sách sao lưu Oracle Database Full backup hàng đêm (01:00 AM); Incremental backup mỗi giờ; Archive log liên tục cho point-in-time recovery. Retention: 30 ngày. MinIO (file storage) Bucket replication sang storage server thứ hai; Sync hàng giờ. Retention: giữ vĩnh viễn (file PDF báo cáo là tài liệu chính thức). Application config Lưu trữ trong Git repository; appsettings.json không chứa secrets (secrets quản lý qua biến môi trường). Flyway migration scripts Lưu trữ trong Git repository, versioned . 11.5 Kế hoạch khôi phục khi sự cố (Disaster Recovery) Các kịch bản sự cố và phương án khôi phục: Kịch bản Phương án khôi phục Lỗi API Server Load Balancer tự chuyển traffic sang instance khác. Khởi động lại instance lỗi. Không mất dữ liệu do thiết kế stateless. Lỗi Oracle Database Chuyển sang standby database (nếu có). Hoặc restore từ backup + replay archive log. RTO ≤ 4 giờ. Lỗi MinIO File vẫn còn trên storage replication. Chuyển endpoint sang server backup. PDF có thể tái tạo từ SnapshotJson. Lỗi Gotenberg Snapshot giữ trạng thái Draft. Sau khi khôi phục Gotenberg, người dùng nộp lại. Không mất dữ liệu nhập liệu. Mất toàn bộ server Restore từ backup: Oracle (full + incremental) → MinIO (replication) → Deploy API từ CI/CD pipeline → Chạy Flyway migrate. CHƯƠNG 12.
